# 開發經驗

將每次實作中可重複使用的做法記在這裡；每筆經驗需註明適用範圍，避免把原型假設當成通用結論。

## 網頁 3D 原型與 GitHub Pages

- **經驗**：需要部署到 GitHub Pages 的 3D 瀏覽器原型，採 Three.js 搭配 Vite 產生靜態 `dist/`，並在 Vite 設定相對路徑 `base: './'`，可避免 repo 網址含子路徑時 JS／資產路徑錯誤。依賴使用 npm lockfile 固定版本；Actions 建置 `dist/` 後再部署 Pages。
- **適用範圍**：單機或前端展示型 WebGL 遊戲、GitHub Pages 靜態託管。多人即時連線、帳號、狀態持久化仍需獨立後端服務，不能由 Pages 靜態主機提供。
- **本專案應用**：用於初期驗證第一人稱移動、3D 搬運和怪物行為；之後若改用 Unity/Godot 或加入多人後端，需重新評估工具鏈。
- **建置觀察**：未拆分時 Three.js 0.187 原型 bundle 約 572 KB（約 145 KB gzip）。Vite 8 / Rolldown 依套件分成兩個 chunk 後，最大 chunk 約 353 KB，另一個約 206 KB，建置不再出現 500 KB chunk 提醒；gzip 合計約 140 KB，拆分改善單檔大小但沒有大幅減少總載入量，還會增加請求數。加入較大型素材或場景後仍應量測實際載入表現。

## Vite / Rolldown 套件拆分

- **經驗**：Vite 8 以 Rolldown `output.codeSplitting.groups` 將大型依賴分組；可降低最大單一 chunk，避免把單檔警告當成總下載量問題已解決。手動分塊可能影響模組副作用執行順序，須檢查正式建置並做瀏覽器驗收。
- **適用範圍**：Vite 8 / Rolldown 的瀏覽器 ESM 專案；拆分主要改善單檔尺寸和快取邊界，不保證減少總位元組數或改善首次載入。
- **本專案應用**：`vite.config.js` 將 Three.js 套件以 `maxSize: 250000` 分組，建置輸出兩個 Three.js chunk，最大約 353 KB；實際遊戲載入順序尚待瀏覽器驗收。

## 網路迷因素材

- **經驗**：素材加入 repository 前，記錄原始頁、作者、授權名稱／版本、授權連結及修改（例如裁切、縮圖）；把署名放在遊戲內或 `CREDITS.md`。只因圖片能在網路上看見，不代表可自由再發布。
- **適用範圍**：公開遊戲 repo、網站、展示頁及可散布的遊戲素材。正式商業發行前，仍須逐項重查素材授權和人物／商標等權利。
- **本專案應用**：首個迷因素材選用 Wikimedia Commons 上標示 CC BY 2.0 的 Grumpy Cat 像素迷因圖；保留作者 Topher McCulloch、來源頁、授權連結與縮圖使用說明。

## 迭代紀律

- **經驗**：先選一個可玩場景，把移動、互動、目標和失敗／成功循環接通，再擴增角色與關卡；每階段更新 plan，將實作中可重用的教訓回寫本檔。
- **適用範圍**：早期遊戲原型與功能迭代；不取代正式 QA、效能測試或發行前的多平台測試。

## Git 遠端狀態核對

- **經驗**：不要只依賴舊的登入提示或本機分支狀態判斷推送是否完成；用 `git ls-remote --heads origin <branch>` 讀取遠端分支，再和本機 `git rev-parse <branch>` 比對提交，才能確認遠端是否已包含目前版本。工作流程檔存在也不代表 Pages 已成功部署，部署結果需另外查 Actions 執行紀錄或實際網站。
- **適用範圍**：使用 Git 遠端的專案交付、CI/CD 與部署狀態檢查；只確認 Git 物件同步，不代表建置、部署或線上功能驗收成功。
- **本專案應用**：確認 `origin/main` 與本機 `main` 同為 `0e1125e`，因此推送已完成；本機沒有 `gh` CLI，Pages workflow 執行及網站部署仍需透過 GitHub Actions／網站狀態查證。

## GitHub Pages 部署故障定位

- **經驗**：工作流程檔存在且觸發成功，不等於 Pages 已啟用。檢查 Actions run 的第一個失敗步驟；`configure-pages` 取得 repo Pages 設定時回傳 404，應先檢查 repo Settings → Pages 的發布來源。標準 `GITHUB_TOKEN` 不足以自動啟用尚未設定的 Pages，避免用增加權限的長效 token 掩蓋設定問題。
- **適用範圍**：GitHub Pages 自訂 Actions 發布流程；不能由本機建置成功推論雲端權限、Pages 設定或實際部署成功。
- **本專案應用**：遠端唯一 workflow run `44441793824` 在 `actions/configure-pages` 以 404 失敗；已把設定頁選擇 GitHub Actions 記為待管理員完成的外部步驟。

## 可純測試的遊戲規則

- **經驗**：把撤離門檻、移動速度等不依賴畫面或 WebGL 的規則放在純函式模組，使用 Node.js 內建 `node:test` 驗證邊界條件，不必為這些規則引入額外測試框架。
- **適用範圍**：JavaScript／Node 工具鏈中的純遊戲規則；不能取代瀏覽器實際輸入、WebGL 畫面、效能或多人同步測試。
- **本專案應用**：5 項回收門檻、搬運／衝刺速度與方鬍子貓警戒範圍測試通過。

## 第一人稱角色存在感

- **經驗**：第一人稱看不到玩家全身時，可用攝影機附掛的低面數手／爪模型提供角色辨識度和動作回饋；保持在畫面下緣，避免遮擋視線與互動物件。
- **適用範圍**：第一人稱 3D 原型、角色手部不需承載完整骨架或裝備動畫的階段；正式動畫仍應改用 rig 與動畫狀態。
- **本專案應用**：新增攝影機附掛的貓掌模型，隨移動輕微擺動，作為貓咪玩家的第一人稱提示。

## 目標進度回饋

- **經驗**：當回合有明確的數值門檻時，在目前數值旁加入原生 `<progress>`，並提供 `aria-label`；回合重設時清零，目標數值更新時同步進度，讓視覺與輔助科技都能讀到回合進度。
- **適用範圍**：有固定目標值的網頁 HUD／表單流程；若進度是多階段、非線性或不確定，需另外設計對應語意，不能硬套百分比。
- **本專案應用**：回收價值達 20 元即可撤離，新增標示「撤離目標進度」的進度條；達標後原生 progress 會封頂，分數文字仍保留實際回收總額。

## 先定合作驗證範圍

- **經驗**：多人功能開始前，先把第一個可驗證切片寫成短規格，固定測試人數、共同目標、成功／失敗條件與單局流程；將試驗數值和正式平衡分開標示，避免網路同步工作同時承擔未定義的玩法決策。
- **適用範圍**：尚未有多人原型的合作遊戲；不代表設定的數值已平衡，也不能取代真實玩家測試。
- **本專案應用**：將 2 人合作測試、共用回收目標與失敗機會，以及全員撤離條件寫入 `gameplay.md`，供後續同步移動、物品與怪物實作作為暫定驗收基準。

## 暫定創作方向

- **經驗**：在名稱或世界觀仍可變動時，先記下供原型使用的工作名稱、短描述、視覺／聲音原則和內容邊界，並標出何時回頭確認正式方向。這能讓早期素材一致，同時避免把暫定選擇當成定案。
- **適用範圍**：早期遊戲、品牌概念或尚待玩家回饋的視覺原型；正式發行前仍需確認品牌可用性、素材權利和目標受眾回饋。
- **本專案應用**：以「夜班貓隊」與午夜便利商店作為工作方向，並明訂迷因造型原創化、素材授權署名和非納粹化的角色邊界；遊玩測試後再檢視正式名稱與美術。

## 座標化關卡底稿

- **經驗**：把程式內的出生點、出口、障礙物、物品和敵人起點整理成同一座標系的關卡底稿，並附上「待遊玩驗收」項目；這能支援多人同步與地圖討論，但不能代替畫面和尋路驗收。
- **適用範圍**：程序化或灰盒關卡、以世界座標配置互動物件的原型；手工建模地圖仍應補上可讀的區域圖和實際通道量測。
- **本專案應用**：`level-layout.md` 對齊 `src/main.js` 的 26 × 20 商店、三排貨架、8 件戰利品、2 隻怪物和撤離點，並保留可達性、光照與難度作為遊玩驗收事項。

## 分開記錄 AI 現況與反制假設

- **經驗**：敵人規格要分清楚「程式目前實際做什麼」和「玩家可能如何反制」。把觸發距離、警告延遲、追擊速度、停止條件和傷害範圍具體列出，再將反制方式標成待測假設，避免未遊玩就把它寫成既定弱點。
- **適用範圍**：早期遊戲 AI 調整、多人同步前的基準記錄；不取代實際難度測試，也不表示數值已平衡。
- **本專案應用**：`monster-rules.md` 彙整方鬍子貓和鍵盤暴走貓的現行規則，特別註明遮蔽、避障和多人目標選擇尚未實作。

## 重開回合還原物件

- **經驗**：物件被掛到相機或其他移動父節點時，重開回合不能沿用當前 local transform；保存不可變的出生 transform，重設時先還原父子關係，再還原位置、旋轉與可用狀態。
- **適用範圍**：Three.js 場景物件會被重新掛到角色或容器下的重試／重生流程；若有物理引擎，還需同步重設剛體速度和碰撞狀態。
- **本專案應用**：修正倒數結束時仍手持物品後重新開始的路徑，並以純函式測試物品位置、旋轉種子與 active/carried 狀態的重置資料。

## 以相對重量影響搬運速度

- **經驗**：早期原型可先用清楚的相對重量值影響搬運速度，讓價值與搬運代價形成選擇；尚未實作物理重量時不要標示為真實公斤。將速度公式維持為純函式，測試輕重物品與衝刺限制。
- **適用範圍**：單件搬運、尚未有剛體物理的遊戲原型；多物品疊加、坡度和慣性需另行建模與測試。
- **本專案應用**：8 種便利商店戰利品採 5–16 點相對重量，搬運速度依重量降低；HUD 顯示相對重量，分數仍只由物品價值決定。

## 先建本機多人連線切片

- **經驗**：多人 Web 原型可先把靜態客戶端和 WebSocket 即時服務分開；本機驗證房間加入、玩家輸入和房主狀態快照後，再選公開託管商。房主權威可簡化第一個同步模型，但房主斷線會中止遊戲，且不提供防作弊。
- **適用範圍**：小型可信任測試群、2 人合作概念驗證；不適用於需要伺服器權威反作弊、大量併發或持久化進度的正式遊戲。
- **本專案應用**：先用獨立 Node.js WebSocket 服務於本機測 2 人；Pages 繼續提供客戶端，遠端服務和費用留待本機原型驗收後決定。

## 測試 WebSocket 房間中繼

- **經驗**：把建房、加入、房間人數限制、角色可送的訊息及斷線清理放在獨立服務模組，使用 Node.js `node:test` 搭配真實本機 WebSocket client 做整合測試；不需要啟動瀏覽器或連外服務即可驗證協定基本路徑。
- **適用範圍**：使用 `ws` 的 Node.js 房間服務、原型期 WebSocket 訊息路由；不能證明瀏覽器網路權限、反向代理、TLS、WAN 延遲或多人畫面同步正常。
- **本專案應用**：`test/multiplayerServer.test.js` 驗證 2 人房間、輸入與快照方向、第三人拒絕、隊友離開，以及房主斷線後房間關閉；客戶端整合和跨瀏覽器測試仍待完成。
